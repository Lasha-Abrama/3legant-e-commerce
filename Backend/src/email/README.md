# Reusable SMTP email service

Configure these backend environment variables locally and on your deployment:

```dotenv
SMTP_HOST=smtp.your-provider.example
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=your-smtp-username
SMTP_PASSWORD=your-smtp-password-or-app-password
SMTP_FROM=support@your-business-domain.example
SMTP_FROM_NAME=3legant
CONTACT_RECIPIENT_EMAIL=contact@your-business-domain.example
```

Use your email provider's actual credentials and an authorized sender address.
Port 587 with `SMTP_SECURE=false` requires STARTTLS; port 465 normally uses
`SMTP_SECURE=true` for TLS from connection start. Certificate checks remain enabled.
SMTP_FROM is a single address; the optional SMTP_FROM_NAME is its display name.
All four host/user/password/from values must be configured together. Leaving all
four blank disables SMTP; an attempted send then throws a safe 503 error.
SMTP_PORT defaults to 587, SMTP_SECURE to false, and SMTP_FROM_NAME to blank.
Contact Us notifications are delivered to CONTACT_RECIPIENT_EMAIL. When it is
blank, the service uses SMTP_FROM, which is suitable when the sender is also the
company inbox. The customer's address is set as Reply-To so staff can reply directly.

Import `EmailModule` into a feature module and inject `EmailService` into its service:

```typescript
await this.emailService.sendContactConfirmation(customerEmail, customerName);
await this.emailService.sendNewsletterConfirmation(customerEmail);
await this.emailService.send(customerEmail, {
  subject: 'Your update',
  text: 'Plain text update',
  html: '<p>HTML update</p>',
});
```

The built-in templates provide plain text and HTML, escaping names in HTML.
Generic HTML must be generated by trusted backend code; escape any user content.
Call newsletter confirmation only after a subscription is recorded and consent
is obtained. This is an acknowledgement template, not a double-opt-in flow.

The service lazily reuses one transporter and awaits SMTP acceptance. A resolved
send means the provider accepted the message, not that it reached the inbox.
Provider rejection, authentication errors, and connection errors throw a generic
503 without returning/logging credentials, recipients, content, or raw diagnostics.
There are bounded network timeouts and no automatic retries to avoid duplicate
messages when SMTP acceptance is uncertain. Contact submissions report saved-but-undelivered failures. Newsletter subscriptions
track delivery flags and retry failed emails on a later explicit re-submission.

Contact and newsletter routes call this service after persistence. Existing password-reset emails
continue using Resend and its separate RESEND_API_KEY/EMAIL_FROM settings.
Run `npm test -- src/email` for mocked transport/configuration/template tests.
Actual mailbox delivery still requires configuring your provider and a live test.

## Gmail SMTP

Keep these settings in the backend `.env` (already ignored by Git), and configure
the same values in your backend hosting environment. Restart/redeploy after changes.

```dotenv
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=your-sender@gmail.com
SMTP_PASSWORD=your-google-app-password
SMTP_FROM=your-sender@gmail.com
SMTP_FROM_NAME=3legant
CONTACT_RECIPIENT_EMAIL=your-sender@gmail.com
```

Use the sender account's Google App Password, not its normal Google password.
Use the same Gmail address for SMTP_USER and SMTP_FROM unless you have configured
an authorized Gmail send-as alias. Never paste credentials into source, logs, or
commands. Do not change RESEND_API_KEY or EMAIL_FROM: password resets still use Resend.
No Gmail `service` preset is needed: the existing explicit host/port configuration
requires STARTTLS with certificate verification and TLS 1.2 or newer.
See [Nodemailer SMTP documentation](https://nodemailer.com/smtp).

Recipients are not restricted to the sender account or Gmail addresses. The service
accepts any valid single recipient address, subject to Gmail's sending limits,
anti-abuse checks, and recipient-server policies. SMTP acceptance cannot guarantee
inbox delivery. Gmail SMTP should not be treated as an unlimited bulk newsletter sender.

The Contact Us endpoint now saves the submission, sends its full name/email/message
to the company recipient, and sends a separate confirmation to the customer's valid
email address. If SMTP delivery fails, the API returns a safe availability error and
does not expose Gmail diagnostics or credentials.

The Newsletter endpoint sends confirmation for a new subscriber or a pending failed delivery,
and sends the company inbox a separate notification containing the subscriber's
email. Existing subscribers receive an already-subscribed response without duplicate
emails, which prevents repeated form submissions from producing email spam.

## Safe real delivery test

Contact/newsletter routes are wired and send real emails when SMTP is configured.
For an explicit delivery test, run the application's service locally from the
Backend directory using the command below. Set EMAIL_TEST_TO to a
mailbox you control or whose owner has agreed to receive the test (preferably a
different mailbox from the sender). This explicitly sends two confirmation emails;
it does not create a contact record or subscribe anyone. Do not run it in CI.

```sh
EMAIL_TEST_TO=your-controlled-test-mailbox@example.com node -r ts-node/register <<'NODE'
const fs = require('node:fs');
const { ConfigService } = require('@nestjs/config');
const { EmailService } = require('./src/email/email.service');
const { validateSmtpEnvironment } = require('./src/email/email.config');

async function main() {
  const env = require('dotenv').parse(fs.readFileSync('.env'));
  const service = new EmailService(new ConfigService(validateSmtpEnvironment(env)));
  await service.sendContactConfirmation(process.env.EMAIL_TEST_TO, 'Delivery Test');
  console.log('Contact confirmation accepted by SMTP.');
  await service.sendNewsletterConfirmation(process.env.EMAIL_TEST_TO);
  console.log('Newsletter confirmation accepted by SMTP.');
}
main().catch(() => {
  console.error('Delivery test failed; check SMTP settings privately. Do not share raw diagnostics.');
  process.exitCode = 1;
});
NODE
```

Check Inbox and Spam in the recipient mailbox, sender display name, and both messages.
Use the mailbox's original-message view to verify text/plain and text/html MIME parts.
If one message succeeds and the other fails, do not blindly rerun both sends.
Repeat from the deployed backend environment before relying on production delivery;
a successful local test does not verify hosting network access to SMTP port 587.
